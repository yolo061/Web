## 一、信号是什么

Unix 中的**软件中断**叫**信号（signals）**（P198）。各种事件会让内核向进程发信号：用户按键、进程非法操作（除零、越界）、计时器到点等。

常用信号（P199，图 7.15 出现的三个 + 常见的几个）：

| 信号 | 编号 | 从哪来 |
|---|---|---|
| `SIGINT` | 2 | 用户按 **Ctrl-C** |
| `SIGQUIT` | 3 | 用户按 **Ctrl-\\** |
| `SIGALRM` | 14 | 计时器到点（`alarm`） |
| `SIGTERM` | 15 | `kill` 命令默认发的 |

一个进程收到信号后有 **3 种处理方式**（7.7.1，P198）：

1. **默认操作**（一般是终止进程）：`signal(SIGALRM, SIG_DFL)`；
2. **忽略信号**：`signal(SIGALRM, SIG_IGN)`；
3. **调用一个函数**（处理函数 handler）：`signal(SIGALRM, handler)`。

## 二、早期 signal 机制的弱点（7.7.2–7.7.4，P198–202）

理解这些"为什么不够好"，才知道 7.8 节的 sigaction 好在哪：

1. **捕鼠器问题（不可靠信号）**：老系统里处理函数被调用一次后就失效了，要在 handler 里再 `signal(SIGINT, handler)` 重设一次。重设之前到达的信号就会杀死进程（P198）；
2. **多信号的处理不确定**：处理 SIGX 时又来 SIGY 怎么办？再嵌套、忽略还是阻塞？各版本 Unix 答案不同（P199–200）；
3. **被中断的系统调用**：进程阻塞在 `read` 等输入时来了信号，是 read 返回 -1 并置 `errno = EINTR`（AT&T 经典模式），还是自动重启（UCB 模式）？（P202）；
4. 不知道信号**为什么**产生、不能安全地**阻塞**信号集（P202）。

## 三、sigaction：可靠的信号处理（7.8，P203–206）

POSIX 用 `sigaction` 替代 `signal`，参数很像，但通过结构体能精确控制所有行为：

| 项目 | 内容 |
|---|---|
| 目标 | 指定一个信号的处理函数 |
| 头文件 | `#include <signal.h>` |
| 函数原型 | `res = sigaction(int signum, const struct sigaction *action, struct sigaction *prevaction)` |
| 返回值 | -1 失败；0 成功 |

`struct sigaction` 三个关键成员（P204）：

```c
struct sigaction {
    void (*sa_handler)();      /* SIG_DFL、SIG_IGN 或处理函数 */
    sigset_t sa_mask;          /* 处理此信号时要阻塞的其他信号 */
    int      sa_flags;         /* 各种行为开关 */
};
```

`sa_flags` 常用位（P204 表）：

| 标记 | 含义 |
|---|---|
| `SA_RESETHAND | 处理函数被调用时重置（捕鼠器模式，要不要它自己选） |
| `SA_NODEFER` | 处理信号时关闭自动阻塞（允许递归处理） |
| `SA_RESTART` | 被信号打断的系统调用自动重启（BSD 模式，而不是返回 EINTR） |

`sa_mask` 用信号集函数构造：`sigemptyset(&set)` 清空、`sigaddset(&set, SIGQUIT)` 加一个。

书上参考代码 `sigactiondemo.c`（P205）——捕获 Ctrl-C，并且在处理 SIGINT 期间阻塞 SIGQUIT：

```c
/* sigactiondemo.c
 * purpose: shows use of sigaction()
 * feature: blocks ^\ while handling ^C
 *          does not reset ^C handler, so two kill
 */
#include <stdio.h>
#include <signal.h>

#define INPUTLEN 100

main()
{
    struct sigaction newhandler;    /* new settings */
    sigset_t         blocked;       /* set of blocked sigs */
    void             inthandler();  /* the handler */
    char             x[INPUTLEN];

    /* load these two members first */
    newhandler.sa_handler = inthandler;    /* handler function */
    newhandler.sa_flags = SA_RESETHAND | SA_RESTART;  /* options */

    /* then build the list of blocked signals */
    sigemptyset(&blocked);          /* clear all bits */
    sigaddset(&blocked, SIGQUIT);   /* add SIGQUIT to list */
    newhandler.sa_mask = blocked;   /* store blockmask */

    if ( sigaction(SIGINT, &newhandler, NULL) == -1 )
        perror("sigaction");
    else
        while( 1 ){
            fgets(x, INPUTLEN, stdin);
            printf("input: %s", x);
        }
}

void inthandler( int s )
{
    printf("Called with signal %d\n", s);
    sleep(s);
    printf("done handling signal %d\n", s);
}
```

P206 的实验提示：连按两次 Ctrl-C 进程会被**第二个** SIGINT 杀死——因为 `SA_RESETHAND` 让 handler 一次性；把 `SA_RESETHAND` 从 `sa_flags` 里去掉就能一直捕获。Ctrl-\\ 在 handler 处理期间会被阻塞（`sa_mask`），处理完再送达。

## 四、任务怎么写：给 shell 装上信号处理

书 8.5 节 psh2.c 的注释 "New problem: shell catches signals. Run vi, press ^c" 就是本任务的伏笔：shell 和它运行的命令同属一个进程组，**Ctrl-C 发给整组**——命令被杀（正常），但 shell 也被杀了（不正常，看看 bash：Ctrl-C 后提示符还在）。

**目标**：Ctrl-C 杀掉正在运行的命令，但 shell 本体活着。

**思路**：shell（父进程）把 SIGINT 设为**忽略**；子进程在 exec 之前把它恢复成**默认**，于是信号只杀子进程。改动就两处：

```c
/* main 里，进入循环之前（shell 自己不再死于 Ctrl-C） */
signal(SIGINT, SIG_IGN);

/* execute() 的 case 0 里，execvp 之前（子进程要能被 Ctrl-C 杀） */
case 0:
    signal(SIGINT, SIG_DFL);      /* 恢复默认：忽略属性会被 fork/exec 继承 */
    execvp(arglist[0], arglist);
    perror( "execvp failed" );
    exit(1);
```

原理：**忽略（SIG_IGN）这种设置会随 fork 继承、也随 exec 保留**；而"指向函数"的处理函数在 exec 后会复位成默认。所以必须让子进程在 exec 前显式 `SIG_DFL`，否则连 vi 里的 Ctrl-C 都失效了。

建议作业做两个程序（或一个两用）：

1. **演示程序**：把 `sigactiondemo.c` 敲一遍跑通（理解 sa_mask/SA_RESETHAND 的行为，对照 P206 的实验清单）；
2. **shell 加固**：在自己写的 `smsh` 上加上面两处改动，验证 Ctrl-C 只杀命令不杀 shell。

想用 sigaction 实现 shell 的忽略，等价写法：

```c
struct sigaction sa;
sa.sa_handler = SIG_IGN;
sigemptyset(&sa.sa_mask);
sa.sa_flags = 0;
sigaction(SIGINT, &sa, NULL);      /* 比 signal 更明确、更可靠 */
```

## 五、编译与测试

```sh
$ cc sigdemo.c -o sigdemo && ./sigdemo
$   # Ctrl-C：应打印 Called with signal 2...，进程不死
$   # Ctrl-\：SIGQUIT 未被捕获 → 默认动作退出（或被阻塞到处理完）

$ cc smsh.c -o smsh && ./smsh
$ sleep 10
$   # 3 秒后按 Ctrl-C：sleep 被杀、smsh 继续活着出提示符
$   # 再正常跑一条命令确认 shell 没坏
```

## 六、现代 Linux 上的兼容性说明

- 头文件：`signal.h`；`sleep` 在 `unistd.h`（书上老代码没包含也能过，但 `-Wall` 会警告）；
- **glibc 的 `signal()` 已按 BSD 语义实现**（内部帮你重设 handler + 自动重启系统调用），所以书上 7.7 说的"捕鼠器/不可靠信号"现象在现代 Linux 上**复现不出来**——`signal(SIGINT, handler)` 后连按多少次 Ctrl-C 都有效，不需要手动重置。这一节的重点是理解历史，实战用 `sigaction`；
- `SA_RESTART` 很实用：不加它，`fgets`/`read` 会被信号打断提前返回 NULL/-1（errno=EINTR），shell 的主循环要自己处理；加上就自动等输入；
- 处理函数里只用 `write`/`signal` 这类异步信号安全的调用最严谨；教学程序用 `printf` 无妨，但要知道严格来说它不安全（书 7.9 节"防止数据损坏"讲的就是这类问题，P206–209）；
- `kill(pid, sig)` 可以从一个进程给另一个进程发信号（7.10 节 P209），有兴趣可以给 shell 加个内部命令玩。

## 七、小结

- 信号 = 内核发往进程的软件中断；Ctrl-C 是 SIGINT、Ctrl-\ 是 SIGQUIT；
- 三种处理方式：`SIG_DFL`（默认）/ `SIG_IGN`（忽略）/ handler（函数）；忽略属性会被 fork 和 exec **继承**，函数 handler 在 exec 后复位；
- 老的 `signal` 不可靠（捕鼠器、EINTR、多信号不确定）；POSIX 的 `sigaction` 用 `struct sigaction` 把 handler、`sa_mask`（阻塞集）、`sa_flags`（如 `SA_RESTART`/`SA_RESETHAND`）一次说清；
- 在 shell 里的应用：父进程 `SIG_IGN` + 子进程 exec 前 `SIG_DFL`，实现"Ctrl-C 杀命令不杀 shell"。
